## A. TOP-3 ПРОДУКТОВЫХ ФИЧИ (Strategist + Lead, validated by Personas)

### 🥇 #1 — Перераспределение остатков с ROI-дашбордом

> Источник: `REDISTRIBUTION_PLAN.md`. Cost: L (3-4 нед core + 1-2 нед polish).

**Что делаем:** связка **прогноз спроса → план перераспределения → автобронь в окнах 09:00/18:00 МСК → ROI-дашборд по факту**. Используем имеющиеся ETL/WB-client/Bot.

**Уникальность.** На рынке 7 ботов (QuotaBot, WBCON, Супербот, А-КОРП, …) делают только автобронь. MPStats / Eggheads — только план. **Никто** не показывает ROI в рублях: «заплатил +0.5% × оборот = X₽, сэкономил Y₽ на логистике, прирост выручки оценочно Z₽». Это брешь рынка.

**Persona validation:**

| Persona | Нужна? | Почему | Frequency | Готов платить |
|---|:-:|---|---|:-:|
| **Selller** | ✅✅✅ MUST | Подключение услуги +0.5% от ВСЕХ продаж — большой коммит, нужно «окупается ли». Сейчас слепо платят | ежедневно (после подключения) | ✅✅ |
| **Manager WB** | ✅✅✅ MUST | Ежедневный workflow — мониторинг ИЛ, заявка на слот. Сейчас ручной обзвон/копипаст из ЛК | 2× в день (09:00 / 18:00) | n/a (не платит) |
| **ROP** | ✅✅ | Хочет показать собственнику «вот ROI инвестиции» | еженедельно | ✅ |
| **Accountant** | ❌ | Не его зона | — | — |

**Кому продаём.** Любой селлер с оборотом ≥5М/мес который уже подключил или думает подключать опцию WB. Сегмент: 50-500 SKU, FBO.

**Риск.** Session-capture API WB — серая зона (WB может прикрутить). Mitigation: имитация официально разрешённого браузерного UX + rate-limit на нашей стороне.

**Связь с другими docs.** Совпадает с CE «не делать AI-фотограф, делать что у Eggheads нет» — у Eggheads ЦУП есть, но без ROI-замыкания и автоисполнения через session-capture.

### 🥈 #2 — Чарджбэки/штрафы/списания WB — лента + workflow оспаривания

> Источник: `STRATEGY_COCKPIT.md` §5.3. Cost: M (3-4 нед, без новых интеграций).

**Что делаем:** парсинг `wb_report_detail.supplier_oper_name` по словарю проблемных операций (Штраф, Удержание, Корректировка, Прочие удержания) → лента с фильтрами → workflow (новое → подана претензия → ответ WB → решено) → PDF/Excel «Реестр претензий за период» для отправки в WB-поддержку → алерт в Telegram при списании > N₽.

**Уникальность.** Profitter и Seller24 показывают штрафы списком, но без workflow / без exportable реестра / без алерта в Telegram. WB-кабинет показывает только текущий месяц, без истории и поиска. **Никто** не даёт «pre-built досье для оспаривания».

**Persona validation:**

| Persona | Нужна? | Почему | Frequency | Готов платить |
|---|:-:|---|---|:-:|
| **Selller** | ✅✅✅ MUST | «Где мои деньги? Почему пришло меньше?» — главная боль. Сейчас разбирает в Excel вручную | еженедельно | ✅✅ |
| **Manager WB** | ✅✅✅ MUST | Часть ежедневной операционки — реакция на штрафы. Сейчас узнаёт через 1-2 нед | ежедневно | n/a |
| **Accountant** | ✅✅ | Для базы УПД и налоговой корректировки. Списания должны классифицироваться: «оспоримое / необратимое» | ежемесячно | ✅ (через бух-канал) |
| **ROP** | ✅✅ | Контроль убытков по менеджерам (у кого больше штрафов = разбор) | еженедельно | ✅ |

**Кому продаём.** Универсально для всех селлеров — у всех есть штрафы. Selling angle: «верните 3-7% бюджета через оспаривание». Окупает подписку в 10 раз.

**Связь с другими docs.** STRATEGY_COCKPIT §5.3 + CE «аудит-режим» (это его подмодуль) + REDISTRIBUTION «WB слепо списывает — нужна прозрачность».

### 🥉 #3 — Аудит-режим: P&L ↔ WB-кабинет ↔ Бухгалтер копейка-в-копейку

> Источник: `COMPETITIVE_TRUESTATS.md` §5 «обходной ход». Cost: M (2-3 нед).

**Что делаем:** новый экран `/audit` — 3 колонки side-by-side:
- Левая — наш P&L (final-логика)
- Средняя — WB-кабинет (через docs-API или manual import XLSX «Реализация»)
- Правая — XLSX бухгалтера (через настраиваемый mapping колонок)

Подсветка строк с Δ > 0.01₽ + дроп-даун «принять WB / принять наш / принять бухгалтера» с записью решения в `audit_log`.

**Уникальность.** TrueStats честно говорит «не бух-сервис». Eggheads — для маркетологов, не для финдиректоров. MPStats — про разведку ниш. **Никто** не даёт связку «селлер + WB + бухгалтер сходятся в одной точке». Это наш **главный USP** уже сегодня (Reconciliation Δ 0₽ с WB + Δ 0₽ с методикой Стаса), нужно превратить в видимый экран.

**Persona validation:**

| Persona | Нужна? | Почему | Frequency | Готов платить |
|---|:-:|---|---|:-:|
| **Accountant** | ✅✅✅ MUST | Главная ежемесячная задача — свести три источника. Сейчас вручную в Excel часами | ежемесячно | ✅✅✅ через бух-канал |
| **Selller** | ✅✅ | «Спать спокойно перед налоговой», доказательство чистоты бух-учёта | ежемесячно | ✅✅ |
| **ROP** | ✅ | Показать собственнику что цифры менеджеров честные | ежеквартально | ✅ |
| **Manager WB** | ⚠️ | Не его зона, но косвенно нужно для kpi | — | n/a |

**Кому продаём.** Селлеры с оборотом 20-200М/год где собственник = бухгалтер или работает с бухгалтером в постоянном диалоге. Это **наш самый чистый USP** для продажи через бухгалтерские каналы (Клерк, ЛуЧет).

**Связь.** Расширяет существующий `pnl_reconciliation.py` + `tax_report_*`. Лёгкая надстройка над уже работающей логикой — главная ценность в визуализации и workflow.

## B. TOP-3 АРХИТЕКТУРНЫХ / ТЕХНИЧЕСКИХ ФИЧИ (Lead-only)

Фокус Lead: что должно быть сделано на технической стороне ДО / ПАРАЛЛЕЛЬНО продуктовой работе, чтобы не утонуть в техдолге при росте.

### 🥇 Tech #1 — WB Sunset миграции (две, дедлайны < 8 недель)

> Источник: `ROADMAP.md` P0, `WB_API_REFERENCE.md` §9. **Безусловный приоритет** — без них сервис ломается.

| Дата | Что отключают | Замена |
|---|---|---|
| **2026-06-23** | `GET /supplier/stocks` | `POST /api/analytics/v1/stocks-report/wb-warehouses` (host `seller-analytics-api`, scope `Analytics`) |
| **2026-07-15** | `GET /supplier/reportDetailByPeriod` | `POST /api/finance/v1/sales-reports/detailed` (host `finance-api`, scope `Finance`, **async** create→status→download) |

**Объём работы.**
- Новая категория `Analytics` в `WbApiClient` + rate-limiter
- Новая категория `Finance` уже частично есть (видно по `integrations/wb/finance`)
- Refactor `sync_stocks` + `sync_report_detail` (последний — async polling, camelCase response, money как string)
- **Бонус:** регион-распределение запасов (бесплатно прилетает к новому stocks-endpoint), закрывает Eggheads-ЦУП флаг

**Risk без миграции:** дашборд / P&L / reconciliation сломаются → отток клиентов в часах после deadline.

**Дополнительный win:** stocks-warehouses данные → база под продуктовую фичу #1 (перераспределение) и под идею «приоритет склада» из Evirma.

### 🥈 Tech #2 — Event bus (Redis Streams) + сегрегация Celery очередей

> Источник: `STRATEGY_COCKPIT.md` §7.2 + §7.3. **Архитектурное решение принимать СЕЙЧАС, до второго нового модуля.**

**Проблема.** При расширении на 3+ модуля (перераспределение, чарджбэки, аудит-режим, дальше биддер/отзывы) без шины событий код «слипнется» — каждый модуль будет poll'ить БД, чтобы реагировать на «новая продажа», «остаток упал», «новое списание». Это N² сложности.

**Что добавляем:**

1. **Redis Streams** как event-bus (надёжнее Pub/Sub, есть consumer groups). События:
   - `sale.new`, `stock.low`, `chargeback.detected`, `tax.deadline.upcoming`, `bidder.rule.fired`, `redistribution.window.open`, `feedback.negative`
2. **Сегрегация Celery очередей** — добавить под продуктовые фичи:
   - `worker-bidder` (конкуренция = 1, отдельная rate-limit логика)
   - `worker-redistribution` (окна 09:00/18:00 МСК — критично НЕ блокировать `sync_report_detail`)
   - `worker-chargebacks` (фоновая работа по парсингу wb_report_detail)
3. Каждый модуль — отдельная папка `docs/modules/<name>.md` со схемой таблиц, listened/published событиями, WB API endpoints, rate-limits.

**Cost:** M (2-3 нед инвестиции, разовая). Окупается с первого же модуля после #1.

**Risk без этого:** через 6 модулей будет slippery monolith, рефакторинг XL.

### 🥉 Tech #3 — Tests for critical paths + Feature flags per-tenant + Триал-механика

> Объединённый блок: «безопасность роста». Источники: `ROADMAP.md` §«Качество кода», `STRATEGY_COCKPIT.md` §7.1, `COMPETITIVE_TRUESTATS.md` §5.

Три связанных задачи, каждая XS-S, вместе формируют **подушку для безопасного запуска продуктовых фичей**:

#### 3a. Tests for critical paths (S → M)
Сейчас покрытие near-zero. Когда добавим биддер / редистрибуцию / чарджбэки — каждый деплой рискует поломать P&L/reconciliation/metrics. Минимум:
- `pnl_builder.py` — все формулы subtotals (gross_profit, EBITDA, …)
- `pnl_reconciliation.py` — Δ 0% инвариант
- `metrics.compute_dashboard` — Final mode на эталонных данных
- `cogs_weighted.cost_for_date` — versioning
- `excel_io` — round-trip по 14 справочникам

**Cost:** M (2-3 нед на core + поддержание).

#### 3b. Feature flags per-tenant (S)
- `tenant_modules(tenant_id, module_code, enabled, expires_at)`
- API guard `Depends(require_module("redistribution"))`
- UI меню генерируется из enabled-модулей
- Готовит почву под модульную тарификацию (Core + Tax + Реклама + Команда — STRATEGY_COCKPIT §8)

**Cost:** S (1 нед).

**Зачем сейчас:** при включении продуктовых фич #1-#3 не у всех клиентов — нужен механизм per-tenant включения/выключения.

#### 3c. Триал-механика + промокоды (XS)
- `tenants.trial_until DATE` + `subscription_status ENUM('trial','active','expired','frozen')`
- `promo_codes(code, discount_pct, days_added, max_uses, used_count, valid_until)`
- Banner «Триал заканчивается через N дней»
- Middleware блокирует API при `expired` (whitelist `/auth/*`, `/billing/*`)

**Cost:** XS (1-2 дня).

**Зачем:** без триала конверсия signup→pay упирается в 0. Это **критический рычаг** для любого product-launch (см. TrueStats §5 Sprint 1).

## C. Рекомендованная последовательность (8-12 недель)

```
Неделя 1-3   Tech #1 — sunset миграции (DEADLINE 23.06 / 15.07)
             + Tech #3c (триал-механика, 2 дня — паралельно)

Неделя 4-5   Tech #2 — event bus + Celery queues (фундамент для product)

Неделя 6-8   Product #2 — Чарджбэки/штрафы (быстрая ценность, без новых интеграций)
             + Tech #3a (тесты на критические pnl-пути — параллельно)

Неделя 9-12  Product #3 — Аудит-режим (использует существующий reconciliation)
             + Tech #3b (feature flags — для постепенного раскатывания)

Неделя 13-16 Product #1 — Перераспределение с ROI (самый сложный, нужны рабочие #2+#3)
```

**Логика порядка.**
- Tech #1 — дедлайны, безусловный приоритет
- Tech #3c — без триала product-launch не имеет смысла  
- Tech #2 — фундамент должен быть готов ДО product #1 (там событийная природа критична: окно открылось → бронируем)
- Product #2 раньше #1 — быстрее ценность, меньше риск, есть данные уже сейчас
- Product #3 — лёгкое (использует существующее), готовится к запуску в сегмент «бухгалтер»
- Product #1 — последним: технически сложнее всех, requires #2 готовый
