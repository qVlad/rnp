## Плановая юнит-экономика (UNIT-план)

**Раздел в сервисе:** меню «SKU и продажи» → **Плановая юнит-эк.** (`/unit-plan`).

### Что это

Полная **плановая** юнит-экономика на основе методики LeymanKids — 60
колонок расчёта по каждому SKU: от базовой цены до итоговой прибыли и маржи.
Источник правды для «сколько мы заработаем при текущих ценах и тарифах».
Идентична Excel-эталону клиента — те же поля, формулы, правила округления.

Это **не** «факт за период» (для этого есть `/units`) и **не** ad-hoc-калькулятор
одной карточки (для этого `/unit-calculator`). Это **forward-looking план** — снимок
«как должно быть сейчас при текущих настройках».

В шапке странице — глобальные константы (WB Клуб %, СПП, эквайринг, налог,
НДС, приёмка), которые применяются ко всем SKU. Их редактирует Собственник
через `/settings`.

Цены тянутся **автоматически** из WB Prices API (sync каждые 30 минут) —
ничего вручную вводить не нужно. Если у SKU нет свежей цены — fallback на
последнюю реальную продажу. Бейдж рядом с базовой ценой показывает источник
и время последнего обновления.

### Зачем использовать

- **Понять «сколько я зарабатываю на каждом SKU сейчас»** — без выгрузки в
  Excel, без ручных расчётов. Открыли страницу — увидели прибыль/маржу
  по всему портфелю.
- **Найти убыточные SKU** — сортировка по марже, цветной highlight
  отрицательной прибыли. Решение: повысить цену, снизить скидку, поменять
  склад, архивировать.
- **Прогноз стокаута** — колонка «Закончится через N дней» помогает
  планировать поставки. Сразу видно какие артикулы скоро уйдут в out-of-stock.
- **Sensitivity-анализ через overrides** — можно для конкретного SKU
  переопределить склад / литры / СПП / FBS-флаг и сразу увидеть, как
  изменится unit-экономика.
- **Snapshot'ы для сравнения** — заморозить «как есть сейчас», через
  неделю/месяц сравнить с текущим состоянием (Δ маржи, Δ прибыли).

### Как настроить (Собственник, один раз)

1. **Откройте `/settings`** → раздел «UNIT-план константы». Заполните
   глобальные параметры: WB Клуб %, СПП, WB Кошелёк, эквайринг, ИЛ-коэф,
   ИРП-коэф, % рекламы, налог, НДС, приёмка ₽/л.
2. **Заполните `volume_l` (литры на штуку)** для каждого SKU — через
   `/settings` → Excel I/O products → импорт, или вручную через
   override на странице `/unit-plan`. Без `volume_l` не будут считаться
   логистика и хранение.
3. **Заполните COGS** — через `/cost-history` или Excel I/O.

### Как работать (ежедневно, РОП / Менеджер)

1. Откройте `/unit-plan`.
2. **Шапка** показывает текущие глобальные константы (read-only chips).
3. **Health-индикатор цен:** «Цены WB: обновлены X мин назад (Y из Z SKU)».
   Зелёный = ОК. Если жёлтый/красный — кнопка **«🔄 Обновить прайсы»**.
4. **Таблица:** 60 колонок, можно скрывать / переставлять. Frozen первые
   6 колонок (склад, литры, бренд, предмет, артикулы).
5. **Фильтры** сверху: по бренду, складу, ABC, сезону. Quick-filters:
   «Убыточные», «Out-of-stock», «Без литров», «Без COGS».
6. **Override per-SKU** — клик на иконку → попап с полями (склад,
   литры, СПП, is_fbs, ABC-метка, сезон). Сохраняется в БД, виден всем.
7. **Snapshot** — кнопка «📸 Заморозить» в шапке → создаёт снимок
   состояния. Через drawer «Snapshots» можно сравнить с текущим (diff
   по марже/прибыли + diff по глобальным константам).

### Полезно для

- **Собственник:**
  - Главный инструмент управленческого учёта.
  - Видит совокупную картину прибыли по портфелю — где маржа просела,
    что архивировать, где поднимать цену.
  - Настраивает глобальные константы (ставка налога, НДС-режим, % рекламы)
    — они автоматически применяются ко всем SKU.
  - Сравнивает snapshot'ы «было/стало» при стратегических решениях.
- **РОП:**
  - **Daily workflow:** утром открыл — увидел весь ассортимент с прибылью.
  - Выявляет проблемные SKU и передаёт менеджерам конкретные действия:
    «#12345 убыточен — повысить цену», «#67890 закончится через 3 дн — заказать».
  - Использует фильтр по бренду чтобы видеть scope каждого менеджера
    отдельно.
- **Менеджер бренда:**
  - Видит только свои бренды.
  - Через override меняет склад / параметры → видит влияние на маржу
    своих SKU.
  - Использует «Закончится через N дн» для планирования поставок.
- **Бухгалтер:** не использует (нет доступа — это управленческий раздел,
  не налоговый).

### Возможности

- **60 колонок** Excel-методики 1:1 с эталоном LeymanKids.
- **Авто-цены** из WB Prices API (sync каждые 30 мин, TASK-LEAD-074) +
  бейдж источника (●/◐/?) + кнопка ручного sync.
- **Глобальные константы** — один раз настроил, применяется ко всем SKU.
- **Override per-SKU** — изменения вручную (склад, литры, СПП, FBS, ABC,
  сезон) для конкретного артикула.
- **Snapshot'ы** — заморозка состояния + diff с текущим. Заморозка
  включает глобальные константы (если их потом поменяли — diff покажет).
- **Quick-filters** — Убыточные / Out-of-stock / Без литров / Без COGS.
- **Drill-down** на конкретный SKU — история цен, COGS, план vs факт.
- **Column visibility + DnD** — настройка таблицы под себя (сохраняется
  в браузере).
- **Прогноз стокаута** — `(остаток × buyout%) / velocity` в днях.
- **Excel-экспорт** — для тех кому нужно «как в эталоне».

### Связанные разделы

- **`/units`** (Юнит-экономика факт) — выручка/прибыль за **прошедший** период.
  Используется для сверки «план vs факт».
- **`/unit-calculator`** — ad-hoc «что если» для одной карточки.
- **`/abc-analysis`** — классификация SKU по выручке/марже A/B/C.
- **`/cost-history`** — управление COGS, который тянется в UNIT-план.
- **`/settings`** → «UNIT-план константы» — глобальные параметры
  (видно только Собственнику).
- **Полная методика** — `UNIT_PLAN.md` в корне репозитория.

## Калькулятор рентабельности WB-акций

**Раздел в сервисе:** меню «SKU и продажи» → **Калькулятор акций**
(`/promo-calculator`). Полная методичка — [`PROMO_CALCULATOR.md`](PROMO_CALCULATOR.md).

### Что это

Симулятор «вступать ли в WB-акцию». Вы выбираете артикулы, указываете
параметры акции (скидка %, длительность, ожидаемый рост продаж) — сервис
показывает per-SKU как изменится маржа: будет ли акция прибыльной, и какой
минимальный рост заказов нужен чтобы выйти в ноль.

### Зачем использовать

- WB регулярно приглашает в акции со скидкой 10-30%. Без расчёта легко уйти
  в минус (особенно по SKU с тонкой маржой).
- Понять **breakeven boost** — «при каком росте продаж в 1.5× / 2× / 3× акция
  окупится». Если ваша среднестатистическая акция даёт +50% продаж, а
  breakeven = +120%, то участвовать не стоит.
- Сравнить per-SKU: акция может быть прибыльной для одних артикулов и
  убыточной для других — отказаться от части.

### Как настроить

1. Откройте `/promo-calculator`.
2. **Выберите SKU** — можно multi-select из таблицы (поиск по nm_id /
   артикулу).
3. **Параметры акции:**
   - Скидка % (обычно 10-25%).
   - Длительность акции в днях (опциональный параметр).
   - Ожидаемый рост заказов (boost), % — например +80% (типично для WB).
4. **Baseline-период:** 7 / 14 / 30 дней — за какой период берём «как было
   без акции».
5. Кнопка **«Симулировать»** → получаете таблицу: текущая маржа vs маржа в
   акции + дельта + breakeven boost.

### Как читать результат

- **Зелёный фон строки** — акция прибыльна для этого SKU.
- **Красный фон** — убыток при таком сценарии.
- **Breakeven boost** — минимальный рост продаж, при котором акция окупается.
  Если ваш типичный boost от акций ниже этого числа — не участвовать.
- Колонка **«Прибыльных SKU»** в сводке: «5 из 10» — стоит ли вообще
  входить, или часть SKU исключить.

### Полезно для

- **Собственник:** стратегическое решение «участвуем ли в акции 22% к
  большой распродаже». Видит совокупную дельту маржи по портфелю.
- **РОП:** распределяет участие между менеджерами — кому какие SKU взять в
  акцию, чьи исключить.
- **Менеджер бренда:** прямой инструмент — посчитать ROI акции до участия,
  передать РОПу список «эти SKU убыточны, исключаем».
- **Бухгалтер:** не использует (это управленческий инструмент).

### Возможности

- Multi-select артикулов.
- Sandbox/preview — расчёт без сохранения, можно перебрать 5-10 вариантов.
- Сортировка по `delta_margin desc` — сразу видны лидеры.
- Опциональный preload активных акций из WB Promo Calendar API (если
  доступен) — иначе manual-input.

## Еженедельный отчёт менеджера

**Раздел в сервисе:** меню «Отчёты» → **Еженедельный отчёт** (`/weekly-report`).

### Что это

Компактный digest за выбранную неделю — для понедельника-утра.
Включает: 10 ключевых KPI с дельтами к прошлой неделе (WoW), Top-5 SKU по
выручке, Top-5 SKU по марже, активные алерты, поле для комментария менеджера,
кнопка экспорта в PDF.

### Зачем использовать

- **Менеджер** открывает в понедельник, видит как прошла прошлая неделя по
  его бренду, добавляет комментарий «была акция, X сел в out-of-stock»,
  экспортирует PDF и отправляет РОПу.
- **РОП** просматривает прогресс по всем менеджерам за неделю.
- Не нужно собирать «недельную сводку» вручную.

### Как настроить

1. Откройте `/weekly-report`. По умолчанию открыта **последняя закрытая
   неделя** (понедельник-воскресенье).
2. Навигация: кнопки `← неделя` / `неделя →` / `⏎ к текущей`.
3. Если вы менеджер — отчёт автоматически по вашим брендам. Если РОП /
   собственник — по всему юрлицу.
4. **Комментарий за неделю** — текстовое поле под алертами. Сохраняется на
   сервере — виден всем в команде (РОП открывает ту же неделю и видит, что
   написал менеджер). Поле «автор · N мин назад» показывает, кто и когда
   редактировал. Кнопка **«Сохранить»** активна только при изменениях.
5. Кнопка **«Скачать PDF»** — генерирует файл `weekly-report-YYYY-MM-DD.pdf`.

### Как читать

- **KPI с WoW дельтой** — стрелка ▲ зелёная = выручка/маржа/orders выросли
  (хорошо), стрелка ▼ зелёная = returns/DRR/expenses снизились (тоже
  хорошо). Цветовая логика учитывает «направление улучшения» per метрика.
- **Top-5 SKU** — увидеть кто тянул вверх, кто вниз.
- **Алерты** — что требует действия (out-of-stock, DRR > 20%, аномалии).

### Для РОПа: scoreboard по менеджерам (TASK-LEAD-061)

Над KPI-сеткой (видна только для **head_of_sales / director**) — таблица
**«По менеджерам»** со всеми активными менеджерами тенанта:

| Колонка | Что показывает |
|---|---|
| Менеджер | Имя/username активного менеджера. |
| Бренды | Список брендов из `brand_assignments`. «не назначены» — менеджер без бренда, цифры нули, уходит в хвост таблицы. |
| Выручка | `revenue_net` за выбранную неделю по его брендам (mode=final). |
| Маржа | Сумма маржи и % к выручке. |
| WoW выручки | ▲/▼ дельта vs. предыдущая закрытая неделя (`week_start - 7 дней`). |
| WoW маржи | Дельта margin% (п.п.). |
| Заказов / Возвратов | Кол-во за неделю. |

**Сортировка:** клик по любому заголовку — toggle asc/desc. По умолчанию —
выручка desc. Менеджеры без брендов всегда внизу.

**Где брать данные:** endpoint `GET /api/weekly-report/by-manager?week_start=YYYY-MM-DD`
(только director/head). Группировка через `brand_assignments` (один
manager → N брендов). Если у тенанта нет назначений — empty state с
ссылкой на `/brands`.

### Полезно для

- **Собственник:** weekly health-check без открытия 10 разделов.
- **РОП:** scoreboard по менеджерам (см. выше) + сводный KPI юрлица.
- **Менеджер бренда:** еженедельная отчётность РОПу — 1 клик «PDF» вместо
  ручного составления Excel.
- **Бухгалтер:** не использует (это управленческий отчёт, налоги — в
  `/taxes`).

### Возможности

- Авто-выбор последней закрытой недели + быстрая навигация.
- Цветные WoW-дельты с правильной семантикой «хорошо/плохо».
- PDF-экспорт (через `html2pdf.js`, рендер прямо в браузере).
- Manager-scope (видит только свои бренды) и head/director-scope (без
  фильтра).
- **Серверный комментарий** (TASK-LEAD-062): виден всей команде, не теряется
  при смене браузера/устройства. Метка автора + времени редактирования.
- **Top-3 рекомендации на неделю** (TASK-LEAD-064): секция в самом верху
  страницы с actionable брифингом. Эвристики: stockout (`#X закончился,
  Y заказов за 30д — нужна поставка`), DRR > 20% (`#X DRR Y% — снизить
  ставки`), возвраты > 30% (`#X возвраты Y% — проверить размерную сетку`).
  Сортировка severity desc → revenue impact desc; максимум 3 шт. Клик по
  рекомендации → `/units?nm_id=X`. Скрыта если рекомендаций нет.
- **Отправка в Telegram** (HYP-002): кнопка «📨 Отправить в Telegram»
  рядом с «PDF». Confirm-диалог со списком получателей →
  HTML-сообщение (KPI + Top-3 + комментарий + ссылка обратно). Director /
  head_of_sales шлёт всем директорам через `services/tg_broadcast.py`;
  manager шлёт в свой личный чат (`users.tg_chat_id`). Если у юзера нет
  привязки TG — fallback на автоматическое скачивание PDF.

## Отчёт по локализации заказов

**Раздел в сервисе:** меню «SKU и продажи» → **Локализация** (`/localization`).

### Что это

Анализ соответствия «склад отгрузки ↔ регион покупателя». Локализация = %
заказов, где склад находится в том же федеральном округе РФ, что и покупатель.
Низкая локализация = дальние перевозки = дорогая логистика + долгая доставка
= ниже buyout %.

### Зачем использовать

- **Узнать «куда отгружать»:** если 60% покупателей из УрФО, а на складе
  Екатеринбург лежит 5% товара — план поставки должен сместиться в
  Екатеринбург.
- **Найти проседающие SKU** — Top-10 артикулов с худшей локализацией.
- **Снижение DRR** — близкие к покупателю поставки = ниже логистика =
  выше маржа.

### Как настроить

1. Откройте `/localization`. Период — последние 30 дней по умолчанию (можно
   изменить через календарь).
2. Главный показатель сверху: **% локализации** (Hero KPI). Хорошо: >70%,
   тревожно: <50%.
3. **Разрезы:**
   - По кластеру (7 кластеров РФ + INTL).
   - По складу WB.
   - По SKU (Top-10 худших — с минимум 5 заказами для статистической
     значимости).
4. **Heatmap** склад × кластер покупателя — сразу видно несоответствия
   (красные ячейки).

### Как читать

- **Hero «% локализации» зелёный (>70%)** — поставки распределены правильно.
- **Жёлтый (50-70%)** — есть резерв оптимизации.
- **Красный (<50%)** — критично: товар лежит не там, где нужно.
- **Heatmap:** красные ячейки = «склад A отгружал в кластер B, далёкий от
  него». Перебалансировать.
- **Top-10 worst SKU** — список артикулов где локализация < 30% при
  значимом объёме.

### Полезно для

- **Собственник:** общий health-индикатор «оптимально ли распределён склад».
- **РОП:** планирование еженедельной поставки — куда грузить чтобы поднять
  локализацию. (Планируется добавить разрез «по бренду» — TASK-LEAD-065 —
  чтобы видеть, у какого менеджера проседает.)
- **Менеджер бренда:** видит свой brand-scope. Скорее **диагностический**
  инструмент — «почему мой бренд плохо доставляется» → подсказка РОПу /
  логисту.
- **Бухгалтер:** не использует.

### Возможности

- Hero KPI + breakdown по 3 разрезам (кластер / склад / SKU).
- Heatmap-визуализация склад × кластер.
- Top-10 worst SKU с brand + предметом + объёмом заказов.
- Cancelled-заказы исключены (не искажают аналитику).
- Brand-filter для менеджера (видит только свои бренды).

### Планируется добавить

- Разрез по бренду / менеджеру (TASK-LEAD-065).
- CTA «Запланировать поставку → /redistribution» с предзаполненным складом
  и nm_id (TASK-LEAD-070).

## Калькулятор стоимости поставок

**Раздел в сервисе:** меню «SKU и продажи» → **Калькулятор поставки**
(`/supply-calculator`).

### Что это

Подсчёт стоимости **обычной (прямой) поставки** партии товара на конкретный
склад WB: платежи за приёмку (доставку до склада) + хранение на складе за
указанный срок. Использует актуальные WB-тарифы.

> Если поставка идёт **через хаб** (транзитная) — используй отдельный
> [Калькулятор стоимости транзитных поставок](#калькулятор-стоимости-транзитных-поставок).

### Зачем использовать

- **Перед оформлением новой поставки** — узнать «сколько отдам WB за
  логистику и хранение». Без этого расчёта вы видите стоимость только постфактум
  в P&L.
- **Сравнить склады:** на какой выгоднее везти партию (планируется
  multi-warehouse compare — TASK-LEAD-068).
- **Прогноз стоимости при изменении WB-тарифов** (планируется WoW δ —
  TASK-LEAD-072).

### Как настроить

1. Откройте `/supply-calculator`.
2. **Выберите склад** (dropdown) — список из официальных тарифов WB.
3. **Параметры партии:**
   - Количество штук в поставке.
   - Литров на штуку — объём одной единицы (важно для расчёта
     по литрам, WB округляет вверх по `ceil`-логике).
   - Длительность хранения (дней).
4. Внизу получаете **per-unit breakdown** (база + дополнительные литры +
   хранение) + **Total ₽** на всю партию.
5. Параметры запоминаются в браузере — пришли завтра, та же партия
   пред-заполнена.

### Что НЕ входит в расчёт

Сноска под результатом честно показывает что **не** учитывается:
- Внешняя логистика (доставка вашим транспортом до пункта приёмки WB).
- Acceptance fee (плата за приёмку, если есть).
- COGS (себестоимость самого товара).
- WB-комиссия (она вычитается при продаже, не при поставке).

### Полезно для

- **Собственник:** изредка — для понимания стоимости логистики при выборе
  склада или объёме поставки.
- **РОП:** при планировании квартальных / месячных поставок — сравнить
  варианты по складам.
- **Менеджер бренда:** при оформлении новой поставки — посчитать
  ориентировочную стоимость для P&L прогноза.
- **Бухгалтер:** не использует.

### Возможности

- Актуальные тарифы (sync с WB ежедневно 08:00 МСК).
- Per-unit breakdown — видно, какая часть приходит на доставку, какая на
  хранение.
- Persist параметров в браузере.

### Планируется добавить

- Multi-warehouse compare — выбрать N складов, увидеть сравнительную
  таблицу (TASK-LEAD-068).
- SKU-aware mode — подтянуть `volume_l` из карточки товара автоматом
  (TASK-LEAD-071).
- Tariff WoW δ — показать «тариф +12% к прошлому месяцу» (TASK-LEAD-072).

## Калькулятор стоимости транзитных поставок

**Раздел в сервисе:** меню «SKU и продажи» → **Калькулятор транзита**
(`/transit-calculator`).

### Что это

Подсчёт стоимости **транзитной поставки** WB — когда вы привозите партию на
**хаб** (Обухово / Шушары / Чашниково / …), а WB сама развозит её
по сети до конечного склада. Тариф транзита считается по литражу партии
с двухступенчатой шкалой (до/от 1500 л).

### Зачем использовать

- **Когда прямой завоз на конечный склад невозможен / неудобен** — например,
  склад в другом регионе, а у вас собственная логистика только до Москвы.
- **Сравнить с прямой поставкой** на тот же склад: калькулятор показывает Δ
  «транзит − прямая», чтобы понять переплату за удобство.
- **Прогноз стоимости при увеличении тарифов** — с 1 апреля 2026 WB поднял
  тарифы транзита в среднем на ~20%, по отдельным направлениям 1.5-2×.

### Как настроить

1. Откройте `/transit-calculator`.
2. **Хаб (транзитный склад)** — впишите/выберите из подсказок (Обухово,
   Шушары и т.д.). Список подсказок дополняется хабами, для которых
   тарифы уже подтянуты из ЛК.
3. **Конечный склад** — выберите из официального списка WB.
4. **Партия:** кол-во штук, литров/шт, дней хранения.
5. **Тариф транзита** — если расширение РНП установлено и вы заходили
   в ЛК WB на страницу «Транзитные направления», тариф подставится
   автоматически (зелёный баннер «📊 Тариф из ЛК WB · обновлён N ч назад»).
   Иначе впишите вручную:
   - Поставки и заказы → Поставки (FBW) → **Транзитные направления**
   - Найдите пару «ваш_хаб → конечный_склад» — там видна ставка ₽/л.
   - Тарифы зависят от объёма: до 1500 л — выше, от 1500 л — ниже.
6. Внизу получаете: стоимость транзита + хранение на конечном складе +
   **сравнение с прямой поставкой** (Δ в ₽).

### Как работает авто-подтягивание тарифов из ЛК

**TASK-LEAD-078 (2026-05-23):** WB Tariffs API не отдаёт тарифы транзита —
их видно только в ЛК. Поэтому используется Chrome-расширение РНП:

1. Установите расширение (см. `/settings` → «Токены для Chrome-расширения»,
   там же ссылка на установку).
2. Откройте в Chrome `seller.wildberries.ru` и зайдите на страницу
   **Поставки и заказы → Поставки (FBW) → Транзитные направления**.
3. Расширение перехватит ответ внутреннего API ЛК, разберёт таблицу
   (хаб → конечный склад → ₽/л) и пошлёт на наш backend.
4. На странице `/transit-calculator` выберите пару — тариф подставится
   автоматически с пометкой «обновлён N ч назад».
5. Уведомление «🚚 Тарифы транзита обновлены» появится один раз при
   первом успешном подтягивании.

**Кто может подтягивать:** только director / head_of_sales (manager —
read-only, видит подтянутое, но обновлять не может).

**Что делать если не подтягивается:** проверь что в `/settings` есть
действующий «Токен для Chrome-расширения», что расширение установлено
и активно (значок в правом верхнем углу Chrome), что ты залогинен в ЛК WB.
Manual ввод по-прежнему работает — впиши тариф руками, как раньше.

### Почему так, а не через API

WB **не отдаёт** транзитные тарифы через публичное API (на 2026-05).
Точный URL внутреннего endpoint'а ЛК не задокументирован — расширение
работает «гибко»: слушает все fetch'и в ЛК и опознаёт таблицу
транзитных тарифов по структуре данных. Если WB поменяет схему — потребуется
обновить расширение, но manual fallback всегда работает.

### Что НЕ входит в расчёт

- Внешняя логистика (ваша доставка до хаба).
- Acceptance fee на хабе.
- COGS товара.
- WB-комиссия при продаже.

### Полезно для

- **Собственник:** оценить переплату за транзит vs прямую поставку.
- **РОП:** планировать многоскладовые поставки через 1-2 хаба.
- **Менеджер бренда:** при оформлении новой партии понять, какой канал
  выгоднее.
- **Бухгалтер:** не использует.

### Возможности

- Compare «транзит vs прямая поставка» на один и тот же конечный склад.
- Двухступенчатая шкала тарифа (до/от 1500 л) с настраиваемым порогом.
- Persist параметров и тарифов в браузере.

### Планируется добавить

- Импорт тарифной таблицы транзита из CSV/XLSX (выгрузка из ЛК WB).
- Авто-подсказка тарифа по сохранённой паре «хаб → склад».
- Multi-route compare — сравнить несколько хабов для одного конечного
  склада.
