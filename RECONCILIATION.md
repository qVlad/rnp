# Сверка P&L с WB-кабинетом — методика

**Маршрут:** [`/reconciliation`](https://rnp.sellerfriends.ru/reconciliation) · **Реализация:** `services/pnl_reconciliation.py` + `pages/Reconciliation.tsx`

Документ описывает что и как сверяет страница «Сверка». Её задача — дать
ответ на вопрос «доверять ли цифрам в P&L?»: совпадает ли наша выручка с
WB-кабинетом до копейки.

См. также: [`USER_GUIDE.md`](USER_GUIDE.md), [`OWNER_GUIDE.md`](OWNER_GUIDE.md),
[`CLAUDE.md`](CLAUDE.md) (раздел «Дашборд KPI и режимы»).

---

## 1. Зачем нужна сверка

Selling on WB: данные, которые видит селлер, размазаны по 3+ источникам:

1. **Дашборд ЛК WB** — оперативные цифры, обновляются раз в N часов.
2. **Финансовый отчёт WB (xlsx)** — единственный «бухгалтерский» документ,
   совпадает с УПД и платёжкой.
3. **Платёжные документы (банк)** — деньги, фактически пришедшие на расчётный
   счёт.

P&L в нашем сервисе строится на источнике #2 (`wb_report_detail`), но
агрегации могут не совпасть с источником #1, если мы где-то налажали с
фильтрами / датами. Страница «Сверка» прямо сравнивает наши цифры с тем
что видит селлер в кабинете WB — **за каждую неделю по каждому SKU**.

## 2. Что сверяется

| Метрика | Источник у нас | Источник WB |
|---|---|---|
| **Выручка gross (₽)** | `SUM(retail_price_withdisc_rub) WHERE supplier_oper_name='Продажа' − …='Возврат'` | дашборд ЛК → «Выручка» |
| **К выплате (₽)** | `SUM(ppvz_for_pay)` | дашборд ЛК → «К перечислению» |
| **Кол-во продаж** | `COUNT(supplier_oper_name='Продажа')` | дашборд ЛК → «Заказы выкупленные» |
| **Возвраты** | `COUNT(supplier_oper_name='Возврат')` | дашборд ЛК → «Возвраты» |

«Сверка по неделям» отдаёт `delta_rub` и `delta_pct` — расхождение. На
закрытых неделях оно должно быть **строго 0₽** (Δ 0%). Если не так — значит:

- В коде живёт устаревший фильтр (`rr_dt` вместо `sale_dt`, отдельные
  `supplier_oper_name` варианты типа `'Добровольная компенсация при возврате'`
  пропущены, и т.д.).
- WB пересчитал отчёт задним числом — например, после жалобы на возврат
  через 2 недели после факта.

## 3. Каноничные предикаты

Все аналитические страницы (Dashboard, P&L, Units, Reconciliation) обязаны
использовать один источник истины для фильтров — модуль
`services/period_aggregates.py`:

- **`OP_SALE`** = `"Продажа"` — продажа товара.
- **`OP_RETURN`** = `"Возврат"` — возврат товара.
- **`OP_COMPENSATION_RETURN`** = `"Добровольная компенсация при возврате"` —
  возмещение клиенту в обход возврата товара (учитывается со знаком минус).
- **`REVENUE_FIELD`** = `retail_price_withdisc_rub` — поле выручки, которое
  совпадает с дашбордом ЛК. Не путать с `retail_amount` (старое поле,
  не учитывает скидку постоянного покупателя).
- **`sale_dt_filter(d_from, d_to)`** — фильтр по `sale_dt` (день
  физического выкупа/возврата). Это **каноничная** дата для группировки в
  operational-режиме. Совпадает с xlsx-выгрузкой WB 1:1.

Если новый сервис читает `wb_report_detail` и **не** использует
`period_aggregates` — Reconciliation поймает расхождение.

## 4. Operational vs Financial reporting mode

Поверх источника данных (preliminary / final / hybrid) есть второй toggle —
**режим отчётности** (TASK-LEAD-054, см. CLAUDE.md):

- **Operational** (default, label «По дню выкупа») — группировка по
  `sale_dt`. Совпадает с дашбордом ЛК.
- **Financial** (label «По дню платёжки») — группировка по `rr_dt` (дата
  строки в финотчёте, она же дата платёжки). Совпадает с разделом WB
  «Финансы → Реализация» + банковской выпиской.

Сверка работает в обоих режимах — но это разные «истины»:

- В **operational** мы сверяем «WB-показал-выкупленным» vs «у нас в P&L».
- В **financial** мы сверяем «WB-зафиксировал-в-фин-отчёте» vs «у нас в P&L».

Расхождения между двумя режимами **на одной неделе** — нормальны. Это
2-недельный лаг между фактическим выкупом и попаданием строки в финотчёт.
Если ты бухгалтер — смотри financial. Если ты собственник / РОП — operational.

## 5. Cross-source виджет (на главной странице)

На /reconciliation в шапке — карточка `ReconciliationHero` с 3 цифрами:

- **Δ%** — относительное расхождение нашей выручки vs WB.
- **Δ₽** — абсолютное расхождение в рублях.
- **Доля выплаты** — `ppvz_for_pay / retail_gross` — какая доля выручки
  реально приходит на расчётный счёт (после WB-комиссии, логистики,
  возвратов). Обычно 50-70%.

Все 3 показателя обязаны быть «зелёными» (Δ% ≤ 0.5%) для последних 4-6
закрытых недель. Если красные — что-то в коде сломалось, открывай таблицу
по неделям и смотри какая недели даёт расхождение → потом drill-down в
SKU-разрез.

## 6. Когда сверка ломается

- **Новый supplier_oper_name появился у WB.** WB иногда добавляет новые
  типы операций (например, `«Сторно продаж»`, `«Корректная продажа»`). Если
  ловишь нулевую сверку → возможно WB ввёл новый тип, надо обновить
  `OP_SALE / OP_RETURN`.
- **Поле выручки изменилось.** WB однажды менял `retail_amount` на
  `retail_price_withdisc_rub` (учёт WB-Кошелька). Сверка показала «всё ОК
  кроме wallet-юзеров» — починили.
- **Финотчёт пересмотрен задним числом.** Иногда WB меняет данные за уже
  закрытую неделю. Сверка покажет «было 0 — стало 50000». Это значит, мы
  держим старую копию и нужно перезапустить sync `wb_report_detail` (через
  Settings → «Sync trigger»).

## 7. Reconciliation imports (TASK-LEAD-051)

На /reconciliation есть журнал импортов — список запросов в WB-API за
report_detail. Кто триггерил, когда, сколько строк подтянулось, ошибки.
Помогает понять «почему сверка вчера прошла, а сегодня нет».

## 8. Cross-tool: PnL vs Tax Report

Реальная боль селлера: «в P&L у меня прибыль 1М₽, а налог считается с базы
1.2М₽». Это нормально:

- P&L (управленческий) — `sale_dt`-based, считает деньги в момент когда они
  заработаны.
- Tax Report — `rr_dt`-based + cash-basis (по платёжкам). У него своя
  логика по 1С / АУСН / УСН.

См. [`TAX_USN_BANK.md`](TAX_USN_BANK.md) /
[`TAX_AUSN_BANK.md`](TAX_AUSN_BANK.md) — там описано почему база может
отличаться от управленческой прибыли.

## 10. Если сверка не сходится — чеклист

1. Проверь `reporting_mode` (footer Layout). В operational vs financial цифры
   разные — это **не** баг.
2. Открой /reconciliation в operational-режиме за последние 6 закрытых недель.
3. Если Δ% ≠ 0 на закрытой неделе — drill в неделю → SKU-разрез → найди
   проблемный nm_id.
4. Открой `wb_report_detail` по этому SKU за неделю — глазами сравни с
   ЛК WB → «Финансовые отчёты → Детализация».
5. Если расхождение в `retail_price_withdisc_rub` — возможно WB поменял
   фильтр / поле. Заводи bug в `agents/bugs-dev.md`.
6. Если расхождение в счётчике продаж — проверь `supplier_oper_name` —
   может появился новый тип.
